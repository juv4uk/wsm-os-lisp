# ADR-008: Швидкість розробки, зрілість і вибір мов за сильними сторонами

**Дата:** 2026-11-27  
**Статус:** **PROPOSED** — пропозиція для явного підтвердження власником  
**Власник рішення:** власник проєкту  
**Пов'язано:** [ADR-006](ADR-006-FPC-AS-FOUNDATION-PROPOSAL.md), [ADR-007](ADR-007-RMCONTROL-PCI-CONFIG.md), [#114](https://github.com/juv4uk/wsm-os-lisp/issues/114), [#115](https://github.com/juv4uk/wsm-os-lisp/issues/115), [#116](https://github.com/juv4uk/wsm-os-lisp/issues/116)

---

## 1. Контекст

Власник уточнив 2026-11-27, що час людини є обмеженим ресурсом, а новий проєкт завжди має ризик невдалих гіпотез. Тому WSM OS Lisp має швидко отримувати практичні результати, не вимагаючи від кожного раннього компонента рівня зрілості завершеного продукту.

Водночас швидкість не є тимчасовою фазою, яку можна відкинути після прототипу. Вона важлива протягом усього життя системи.

## 2. Запропоноване рішення

### 2.1. Швидкість — постійна інженерна вимога

Оптимізується повний цикл:

`зміна → компіляція/збірка → тест → feedback → інтеграція`

Вимірювати, де це застосовно:

- час першого (cold) і повторного (warm) запуску;
- інкрементальну та повну компіляцію/збірку;
- час до першого корисного feedback;
- час тестів і повного перевіреного циклу;
- P50 та P90, сирі семпли, конфігурацію середовища;
- час інтеграції та відновлення після невдалого експерименту.

Не оптимізувати окремий компіляторний крок, якщо він не зменшує повний час отримання перевіреного результату. Не порівнювати різні машини або різні режими оптимізації без чіткого розділення.

### 2.2. Якість — доказова міра зрілості

Рекомендовані стани компонента:

1. **EXPERIMENTAL** — гіпотеза або spike; межі ризику названі, результат можна відкинути.
2. **PROTOTYPE** — основний сценарій працює в контрольованому середовищі; є відтворюваний запуск.
3. **VERIFIED** — позитивні й негативні тести, ABI/формат/ownership перевірені; відомі обмеження задокументовані.
4. **STABLE** — контракт сумісності визначений, регресійні тести й відтворювані збірки працюють, є план підтримки.
5. **MATURE** — тривалі експлуатаційні докази, безпека, відновлення, сумісність і продуктивність підтверджені на цільових сценаріях.

Стани не є односпрямованою шкалою: нові дефекти або зміна контракту можуть повернути компонент на попередній рівень. Вік, кількість рядків коду чи впевнені формулювання не є доказом зрілості.

### 2.3. Базова коректність не відкладається

Навіть експериментальний компонент зобов'язаний мати межі впливу та безпечний failure path. Не відкладаються:

- захист даних і фізичних носіїв;
- bounded operations та перевірка меж;
- коректність апаратних операцій і ABI;
- негативні тести для небезпечних входів;
- provenance для зовнішнього коду й артефактів.

Оптимізація, широка сумісність та експлуатаційна зрілість можуть нарощуватися поступово; базова безпека — ні.

### 2.4. Вибір мов та інструментів за завданням

Не встановлювати мовної монополії як загального правила. Обирати реалізацію за сумарною вартістю життєвого циклу компонента:

- швидкість feedback і збірки;
- продуктивність та footprint;
- бібліотеки й можливість повторного використання;
- ABI/FFI та складність інтеграції;
- безпека пам'яті й модель конкурентності;
- доступність налагодження, тестування та підтримки.

FPC може бути вигідним для швидкої нативної розробки Pascal-компонентів; C — для повторного використання зрілих бібліотек і драйверів; Assembly — для вузьких архітектурних механізмів. Жодна інша мова не потребує окремого дозволу лише через свою назву: усі мови відкриті для використання в будь-якому шарі. Придатність конкретної реалізації підтверджується ABI, тестами, безпекою та вимірюваннями згідно з [ADR-009](ADR-009-OPEN-LANGUAGE-AND-CODE-REUSE.md).

Не стверджувати, що C-код компілюється FPC: кожен компілятор компілює свій вихідний код. Перевага багатомовного підходу — швидкий цикл власного коду плюс повторне використання перевірених компонентів через явні контракти.

### 2.5. Повторне використання перед переписуванням

Готовий компонент переважає нову реалізацію, якщо він:
- має сумісну ліцензію та provenance;
- відповідає потрібному target/ABI або може бути ізольовано адаптований;
- проходить необхідні тести й безпекову перевірку;
- не створює неприйнятної вартості залежності.

Переписування дозволене, коли вимірювана користь або технічна несумісність виправдовує його повну вартість.

## 3. Межі цього ADR

Цей документ є пропозицією про процес розробки й критерії вибору інструментів. Він **не** змінює самостійно:

- SENS Contract 12.0 або семантичну владу SENS;
- чинний target ABI/runtime чи boot chain;
- чинний target ABI/runtime, boot chain і семантичну владу SENS; мовні заборони скасовані ADR-009;
- вимоги evidence gates P0–P4.

Усі мови дозволені; вибір мови не є окремим permission gate. Зміна runtime, ABI, boot chain або семантичної влади все одно потребує відповідного рішення й позитивних/негативних свідків.

## 4. План перевірки

1. #115: виміряти реальний цикл FPC, TCC, Clang і GCC на еквівалентних малих задачах; не робити висновків лише з synthetic compile time.
2. #113: завершити окрему перевірку FPC embedded target та UEFI ABI.
3. #116: довести мінімальну інтеграцію Pascal ↔ C через стабільний ABI, ownership і lifetime.
4. Використати результати для рішення, які інструменти скорочують повний час розробки та де вони придатні.
5. Після результатів повернутися до цього ADR для явної owner-ратифікації або відхилення.

## 5. Критерії прийняття пропозиції

- [ ] Власник підтвердив, що швидкість є постійною вимогою.
- [ ] Власник підтвердив доказову модель зрілості компонентів.
- [ ] Власник погодив правила вибору мов за сильними сторонами.
- [ ] Суперечності з ADR-006/ADR-007 розв'язані явним рішенням, не мовчазною зміною.
- [ ] Метрики швидкості вимірюються відтворювано.
- [ ] Базова коректність і безпека не відкладені до пізньої зрілості.

---

**Примітка:** мовні заборони скасовані директивою власника від 2026-11-27 та відображені в ADR-009. Інші чинні контракти й гейти залишаються обов'язковими.
