# ADR-005: Межа довіри — арбітр, а не «ядро без ядра»
*ADR-005: The trust boundary — an arbiter, not a "kernel-less" system*

**Date/Дата**: 2026-11-26
**Status/Статус**: **PROPOSED** — пропозиція, не директива. Чинною стає лише після рішення власника.
**Supersedes/Заміщує**: нічого. Не змінює [ADR-004](ADR-004-LISP-ASSEMBLY-PURE-ARCHITECTURE.md), не змінює `tasks.lisp`.
**Related**: ADR-004 (production-межа), [#40](https://github.com/juv4uk/wsm-os-lisp/issues/40) (пристрійна capability-вертикаль), [#41](https://github.com/juv4uk/wsm-os-lisp/issues/41) (Banyan), [#58](https://github.com/juv4uk/wsm-os-lisp/issues/58)–[#71](https://github.com/juv4uk/wsm-os-lisp/issues/71) (GC), [#78](https://github.com/juv4uk/wsm-os-lisp/issues/78)/[#99](https://github.com/juv4uk/wsm-os-lisp/issues/99) (планувальник), [#109](https://github.com/juv4uk/wsm-os-lisp/issues/109) (Contract 12).

## 1. Context and problem statement / Контекст і постановка проблеми

Власник сформулював архітектурну тезу: **операційна система не повинна заважати програмам виконуватися; її робота — безпечно мультиплексувати залізо, а не нав'язувати абстракції.** Теза має три історичні родичі (exokernel, unikernel, Lisp-машина) і вже частково втілена в цьому репозиторії через ADR-004.

Проблема не в тезі, а в її короткій формі «ОС без ядра». У такій формі зникає одна ланка: **точка примусу**. Правило, яке ніхто не виконує апаратно або механічно, — це коментар, а не властивість системи. Через це виникає небезпека двох протилежних помилок:

1. **Романтизація**: оголосити систему «без ядра» і тим самим оголосити відсутність ізоляції філософією, а не станом.
2. **Регрес**: повернути товсте ядро «заради безпеки» і втратити саму тезу.

Цей ADR фіксує третій шлях: **межа існує, вона названа, вона мінімальна, і кожна політика мусить мати точку примусу в ній.**

### 1.1. What is already a fact in this repository / Що вже є фактом у цьому репозиторії

Це не припущення і не план — це чинний стан, який ADR лише називає явно:

| Механізм | Де | Що доводить |
| :--- | :--- | :--- |
| Lisp-політика поверх провізійованої PCI/BAR/MMIO-можливості | [#40](https://github.com/juv4uk/wsm-os-lisp/issues/40), `scripts/check-mmio-device-op.sh` | Політика пристрою вже відділена від механізму |
| Fail-closed на відсутній фізичній мапі | [#34](https://github.com/juv4uk/wsm-os-lisp/issues/34), `scripts/check-mmio-mutation-fail-closed.sh` | Відмова замість припущення identity mapping |
| Nonce-перевірка capability-дескриптора в асемблері | `src/runtime.s`: `wsm_pci_config_capability`, `0x150434954346` | Перевірка повноважень уже в mechanism layer |
| Закритий словник помилок пристрою/ABI | `scripts/check-semantic-authority.sh` (`MMIO_ERR_*`) | Відмова пристрою відрізняється від мовної помилки Lisp |
| Zero-Rust межа | `scripts/check-no-rust.sh` | Третя мова реалізації відсутня в production |

Тобто «ядро як арбітр» для цього репозиторію — **не нова архітектура, а ім'я для вже зробленого**. ADR-005 не додає механізмів; він забороняє розмивати вже наявну межу і забороняє цитувати те, чого немає.

## 2. Decisions proposed / Рішення, які пропонується прийняти

### D1. Name the boundary instead of denying it / Назвати межу замість того, щоб її заперечувати

Production-межа залишається такою, як у ADR-004, і має рівно дві названі частини:

```text
        ┌──────────────────────────────────────────────┐
        │  Lisp policy  (семантика, політика, драйвери)│
        └──────────────────────────────────────────────┘
                            ↓ generated call
        ┌──────────────────────────────────────────────┐
        │  ARBITER: assembly mechanism layer           │
        │  boot / IDT / ports / MMIO / paging / DMA     │
        │  + capability check + fail-closed return      │
        └──────────────────────────────────────────────┘
                            ↓
                      Bare Metal CPU
```

**Арбітр** — це не «ядро, що керує». Це єдина точка, де система фізично здатна сказати «ні». Твердження «у нас немає ядра» в цьому репозиторії забороняється як неточне: є арбітр, і його розмір є архітектурною метрикою.

### D2. Enforceability rule / Правило примусу

Кожне твердження вигляду «політика X забороняє Y» допускається в документації, README, коміті або звіті **лише** з трьома складовими:

1. **точка примусу** — конкретне місце в `src/*.s` або в admission-коді, яке фізично відхиляє Y;
2. **негативний свідок** — збережений transcript QEMU/хоста, де Y відхилено з конкретним кодом;
3. **гейт** — скрипт у `scripts/`, підключений кроком у `.github/workflows/ci.yml`.

Політика без цих трьох складових — це **намір**. Намір дозволено описувати в `docs/VISION.md`, заборонено цитувати як властивість системи.

Ці три складові живуть у машиночитаному реєстрі [`policy-enforcement.lisp`](../policy-enforcement.lisp), а перевіряє їх [`scripts/check-policy-enforcement.py`](../scripts/check-policy-enforcement.py). Реєстр не вірить сам собі: кожен запис повторно перевіряється проти дерева.

### D3. Single trust domain / Правило одного довіреного світу

Поточний стан: одна адресна область, одна привілейована межа, немає MMU-ізоляції між програмами, немає окремих доменів захисту. Це **явний стан**, а не недогляд.

Доки немає свідка ізоляції (див. D6), заборонено:

- запускати будь-який недовірений код у цьому образі;
- називати щось «процесом» у значенні *захисту* (дозволено: «задача», «потік», «ланка планувальника»);
- оголошувати мульти-тенантність, пісочницю, «безпечне виконання чужого коду»;
- виводити будь-яку гарантію безпеки з наявності capability-перевірки: capability обмежує *цей* механізм, а не весь образ.

### D4. GC stop-the-world is a scheduler event / Збирач сміття = подія планувальника

У Lisp-образі колектор не є бібліотекою: зупинка світу — це глобальна подія планування. Тому:

- жодна «багатозадачність» не оголошується без явного контракту **арен і точок зупину** (яка арена чия, хто може зупинити світ, що відбувається зі стеками під час зупинки);
- дво-задачний handoff ([#78](https://github.com/juv4uk/wsm-os-lisp/issues/78), [#99](https://github.com/juv4uk/wsm-os-lisp/issues/99)) є свідком **механізму перемикання**, а не свідком ізоляції;
- пошкоджений вказівник у драйвері — це пошкоджена купа, а не «впав драйвер»; будь-яке твердження про відновлення після збою вимагає окремого свідка.

### D5. A language guarantee does not cover the arbiter / Мовна гарантія не покриває арбітра

SENS володіє законами мови; target ABI зобов'язаний доводити відповідність свідками ([#109](https://github.com/juv4uk/wsm-os-lisp/issues/109)). Але **типізація найвищого шару не покриває найнижчого**: сирі слова, які арбітр читає з MMIO, не мають домену, поки їх не допущено. Тому:

- «верифікована мова» ніколи не цитується як гарантія безпеки арбітра;
- кожне значення, що приходить із заліза, потребує явного допуску або явної відмови (чинна практика `MMIO_ERR_*` — правильна);
- ADR не дозволяє виводити безпеку системи з безпеки мови.

## 3. Consequences / Наслідки

**Позитивні**

- Межа стає вимірюваною: «арбітр» — це файли `src/*.s` і admission-код, їх можна порахувати й обмежити.
- Зникає клас заяв, які неможливо перевірити: кожна політика мусить мати гейт або не цитується.
- Дослідження (Banyan, XNU, CHERI) перестає бути тихим дозволом: ADR явно відділяє «досліджуємо» від «прийнято».

**Негативні**

- Немає швидкого шляху до мульти-тенантності: спершу механізм ізоляції та його свідок.
- Кожен новий пристрій дорожчає: політика + негативний свідок + гейт, а не лише «працює в QEMU».
- Частина історичних формулювань у документації стає непридатною до цитування (це навмисно).

## 4. What this ADR does **not** decide / Що цей ADR не вирішує

- Не дозволяє імпорт Darwin/XNU і не змінює boot chain (див. [`docs/research/DARWIN-XNU-REFERENCE-FEASIBILITY-2026-11-19.md`](research/DARWIN-XNU-REFERENCE-FEASIBILITY-2026-11-19.md)).
- Не обирає топологію Banyan ([#41](https://github.com/juv4uk/wsm-os-lisp/issues/41)) і не робить динамічне «вкорінення» чинним механізмом.
- Не обирає апаратну базу (CHERI/CHERIoT, MMU-домени, FPGA) — це окреме рішення з окремим свідком.
- Не змінює ADR-004 і не дозволяє Rust або C у production.
- Не є доказом жодного факту про систему.

## 5. PROPOSED → ACCEPTED criteria / Критерії переходу

ADR стає чинним, коли виконано **всі** пункти:

| # | Свідок | Стан |
| :--- | :--- | :--- |
| W1 | Негативний: Lisp-політика намагається MMIO-запис без capability → відмова з `MMIO_ERR_CAPABILITY_WRITE` | частково є (`check-mmio-mutation-fail-closed.sh`) |
| W2 | Негативний: доступ за межі BAR → відмова з `MMIO_ERR_OVERFLOW_*` | частково є (`check-mmio-abi-bounded.sh`) |
| W3 | Позитивний: той самий образ, та сама політика, успішний доступ | є (`check-mmio-device-op.sh`) |
| W4 | **Реєстр «політика → точка примусу → гейт»** у машиночитаному вигляді + гейт, що падає на політиці без точки примусу | **виконано 2026-11-26**: `policy-enforcement.lisp` (8 записів) + `scripts/check-policy-enforcement.py`; гейт пройшов шість негативних тестів (хибний літерал, хибний свідок, статус `intent`, неіснуючий гейт, гейт без воркфлоу, хибна відсутність) |
| W5 | Розмір арбітра зафіксований числом (рядки `src/*.s`) і не зростає без рішення | **виміряно 2026-11-26**: 3751 рядок (36,9 % рукописного коду); поріг «не зростає без рішення» ще не встановлений |

**Фальсифікація ADR**: якщо знайдеться політика, яку система реально примушує **без** точки примусу в арбітрі або admission-коді — теза ADR хибна, і межа описана неправильно.

### 5.1. Вимірювання станом на 2026-11-26

```text
арбітр            src/*.s (entry + runtime + drivers)   3751 рядок
рукописний код    .s + .lisp + .sh + .py без artifacts/  10160 рядків
гейти й тулінг    scripts/*.sh + scripts/*.py            5705 рядків
```

Арбітр — 36,9 % рукописного коду. Гейтів і тулінгу — у 1,52 раза більше, ніж арбітра.

Друге число — не привід для гордості, а ризик: гейти не входять у TCB, але вони входять у площу обслуговування. Для порівняння, у Asterinas (framekernel, USENIX ATC '25) TCB становить близько 14,0 % кодової бази — але там TCB це лише `unsafe`-фреймворк, а не весь механізм. Наші числа не порівнянні напряму; порівнянною є сама практика: **публікувати частку й тримати її під контролем.**

## 6. Lessons from a neighbouring project / Уроки сусіднього проєкту

`omarchy` (37signals) — публічний приклад інтенсивної агентної роботи з іншим рівнем дисципліни. Його помилки переносяться на цей репозиторій без змін, тому фіксуємо їх явно.

| Спостереження в `omarchy` | Клас ризику | Правило тут |
| :--- | :--- | :--- |
| Генеровані bash-скрипти обробляли недовірені дані: у PR #7847 назва відео потрапляла в команду завантаження, у PR #7926 click-action виконувався як shell-рядок | Ін'єкція команд | Жодного `eval`, жодного `sh -c "… $VAR …"`, жодної некаватованої підстановки як команди. Перевірено: у `scripts/` таких місць немає; додано `scripts/check-shell-safety.sh` як гейт, щоб не з'явилися |
| У публічному репозиторії не було жодного CI-воркфлоу: ~444 команди в `bin/`, 76 інсталяторів, лінтер ніхто не запускав автоматично | Тихе накопичення дефектів | Кожен новий скрипт отримує крок у `.github/workflows/ci.yml` у тому самому коміті, що й скрипт |
| 1243 змерджених PR і ~400 у черзі; обсяг зростає швидше за здатність читати | Обсяг ≠ цінність | Заборона нових гілок (наказ власника 2026-10-11) підтверджується цим ADR. Стан гілок зафіксовано в [`docs/BRANCH-INVENTORY-2026-11-26.md`](BRANCH-INVENTORY-2026-11-26.md) |
| У більшості випадків авторство агента не вказане (за дослідженням AI-slop PR — 13,9% розкривають використання AI наперед) | Неможливо відрізнити перевірене від згенерованого | Кожен коміт агента називає себе; кожне твердження має свідока або позначку «намір» |

Головний висновок: **`omarchy` провалився не на генерації коду, а на відсутності гейтів.** Генерація без примусу = борг, який платить власник.
