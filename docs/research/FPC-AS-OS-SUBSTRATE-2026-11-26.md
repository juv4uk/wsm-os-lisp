# FPC як основа ОС і Lisp-машини: перевірка тези
*FPC as an OS and Lisp-machine foundation: verifying the thesis*

**Дата**: 2026-11-26
**Статус**: RESEARCH — перевірка тверджень, не рішення. Не змінює ADR-004 і не дозволяє Pascal у production-межі.
**Стосується**: [ADR-004](../ADR-004-LISP-ASSEMBLY-PURE-ARCHITECTURE.md), [ADR-005](../ADR-005-TRUST-BOUNDARY-ARBITER-NOT-KERNELLESS.md), `juv4uk/wsm-lazarus` (`docs/decisions/2026-09-18-fpc-first-vertical-ADR.md`)

Правило цього документа: кожне твердження перевіряється окремо. Теза «FPC придатний для ОС і дуже придатний для Lisp-машини» розбирається на частини, і кожна отримує один із трьох присудків — **підтверджено**, **перебільшено**, **не підтверджено**. Загальний висновок наприкінці може не збігатися з вихідним текстом, і це нормально.

## 1. Перелік проєктів: що є насправді

| Проєкт у тексті | Що каже текст | Що підтверджується | Присудок |
| :--- | :--- | :--- | :--- |
| **FPOS** | «мінімальне ядро з реалізацією Scheme для драйверів», живий | Репозиторій `rezgui/fpos` існує; README описує мінімальне FPC-ядро та Scheme-компоненти для ATA, PS/2, UART, FAT32 і RTC. GDT/IDT, ISR, IRQ, консоль, клавіатура, memory manager (із приміткою «needs testing»), speaker і RTC позначені як реалізовані. System calls, multitasking і filesystem у чек-листі **не позначені**; автори також попереджають, що відповідні файли multitasking/filesystem не використовуються через непридатний стан. README каже, що проєкт потребує ревізії та нового завантажувача для 64-bit. Це доказ експериментального прототипу й Scheme-драйверів, а не наявності готової багатозадачності чи файлової системи | **підтверджено з істотними застереженнями** |
| **TORO Kernel** | «монолітне ядро x86-64 з SMP і TCP/IP» | Початкове твердження змішує два репозиторії ToroKernel. `torokernel/torokernel` — сучасний x86-64 unikernel для microVM (QEMU-KVM/Firecracker), з cooperative I/O-bound scheduler, virtio-fs/vsock; застосунок працює на тому самому privilege level, без syscall-межі. Окремий `torokernel/ToroOS` — навчальна x86 ОС, README якої прямо вказує одне CPU-ядро; SMP і networking позначені як work in progress. | **частково підтверджено; початковий опис неправильний** |
| **FP-RTOS** | «real-time ядро для ARM» | У поточному проході не знайдено достатньо надійного першоджерела, яке дозволяє перевірити саме цей проєкт, його код, цільові плати та поточний стан. Згадки у вторинних переліках не є доказом реалізації або підтримки. | **не підтверджено першоджерелом** |
| **Ultibo** | «100 % FPC для Raspberry Pi з повним IPv4-стеком і USB» | Офіційний FAQ прямо каже, що Ultibo написаний повністю на Free Pascal; це bare-metal embedded-середовище, не ОС загального призначення. Окремо існує C/C++ API та бібліотеки для прикладного коду — це не заперечує FPC як мову реалізації Core. README описує preemptive threading, SMP на Raspberry Pi 2/3/4, IPv4, USB, файлові системи, DMA та інші периферійні інтерфейси. Сторінка Current Status указує Core 2.6.173 (09.02.2026), FPC Stable 3.2.2 / Fixes 3.2.3 / Main 3.3.1 та C/C++ API 1.0.129 (26.01.2026). | **підтверджено з чіткою межею застосування** |
| **StreamOS** | у тексті **відсутній** | Назва присутня у вторинному переліку ОС на Pascal, але в цьому проході не знайдено перевіреного першоджерела, яке дозволяє підтвердити репозиторій, архітектуру й стан реалізації. | **додаткова неперевірена згадка** |
| **Asuro** | «x86 з NASM лише для bootstrap» | **Не підтверджено** в цьому проході: пошук не дає проєкту ОС із такою назвою (Asuro — відомий як робот c't) | **не підтверджено** |
| **Jacqueline** | «експериментальне ядро з графічним і звуковим стеком» | **Не підтверджено** в цьому проході: пошук не дає такого проєкту | **не підтверджено** |

Висновок по розділу: з шести назв у первісному переліку три мають перевірені першоджерела (FPOS, TORO як два окремі проєкти, Ultibo), а FP-RTOS, Asuro та Jacqueline у цьому проході не підтверджені першоджерелами. StreamOS — додаткова назва зі вторинного переліку, також без незалежно перевіреного першоджерела. «Підтверджено» тут означає існування та описані можливості, а не production-зрілість чи відтворювану збірку.

Першоджерела: [FPOS](https://github.com/rezgui/fpos), [TORO unikernel](https://github.com/torokernel/torokernel), [ToroOS](https://github.com/torokernel/ToroOS), [Ultibo Core](https://github.com/ultibohub/Core), [Ultibo FAQ](https://ultibo.org/faq/), [Ultibo Current Status](https://ultibo.org/wiki/Current_Status). Вторинний список для пошуку додаткових кандидатів: [Operating Systems written in FPC](https://pascal.chat/wiki/Operating_Systems_written_in_FPC); він не замінює першоджерела.

## 2. Технічна таблиця: що перебільшено

| Твердження | Уточнення |
| :--- | :--- |
| «Голий метал: `-Tlinux -Cn` або `-Tembedded`» | Це **різні речі**, подані як рівноцінні. `-Tembedded` — окрема ціль (ARM embedded); `-Tlinux -Cn` — Linux-ціль без виклику лінкера, тобто власний лінкер-скрипт і власний вхід. Обидва підходи вживані, але другий не прибирає RTL: він лише дає вам контролювати лінкування. |
| «Стандартні `.o` (ELF/PE), лінкується з C та асемблером» | Правильно. Саме тому Pascal технічно сумісний із наявним ланцюгом — і саме тому його відсутність у ADR-004 є рішенням, а не технічною неможливістю. |
| «Компіляція за секунди → стратегічна перевага» | Див. §4. У цьому екосистемі це **протокол без жодного заміру**, і власний документ репозиторію забороняє подавати його як перевагу. |
| «Енергоефективність на етапі розробки» | Те саме: це **проєкція** за формулою з названими припущеннями, а не вимір. `wsm-lazarus` має лінію RAPL для джоулів на виконанні, але не для «енергії очікування». |
| «FPC latest» | Офіційна сторінка Free Pascal усе ще називає 3.2.2 останнім stable-релізом; development триває у 3.3.x snapshots без гарантії підтримки/стабільності. Ultibo у своїй матриці вказує Main 3.3.1. Експерименти повинні pin-ити точні версії компілятора й RTL. |

## 3. Головний конфлікт, якого в тексті немає

Текст пропонує FPC як **основу** ОС і Lisp-машини, з гібридом «асемблер + Pascal + C + SENS + Lisp» в одному образі. Це прямо суперечить двом чинним рішенням цієї екосистеми:

| Чинна межа | Що вона каже | Що зробив би текст |
| :--- | :--- | :--- |
| **ADR-004** (`wsm-os-lisp`, ACCEPTED) | Production-межа: **Lisp + x86-64 асемблер**, `RUST = 0`, нуль C у production. Ядро політики — Lisp, механізм — асемблер | Додає **третю** мову реалізації (Pascal) і четверту (C через FFI) у production |
| **ADR «п'ятий субстрат FPC»** (`wsm-lazarus`, PROPOSED) | FPC — **свідок** канону SENS: статистична компіляція, детермінована пам'ять без GC, арена, trampoline. Мета — довести `(canon-conforms?)` → `(canon-conformance satisfied)` | Робить із FPC **основу системи**, а не свідка |

Це не дрібна розбіжність у формулюваннях. Це різні ролі одного інструмента: **свідок** доводить, що семантика відтворюється на іншому субстраті; **основа** визначає, з чого зроблена система. Перше вже прийнято й працює. Друге вимагає скасування ADR-004 — тобто рішення власника, а не висновку агента.

Окремо: текст називає відсутність ізоляції «свідомим вибором» — і це збігається з ADR-005 D3. Але ADR-005 D3 вимагає **назвати** стан («один довірений світ») і забороняє виводити з нього гарантії. Формулювання «когерентність замість ізоляції» як перевага — це саме те, що D3 забороняє цитувати без свідка.

## 4. Найсильніший аргумент тексту — і чому він зараз не аргумент

Аргумент «швидка компіляція = швидка ітерація архітектури» — єдиний, який справді міг би переважити ADR-004. І саме він у цій екосистемі **вже формалізований, але не виміряний**.

`wsm-lazarus/docs/chas-iteratsii.uk.md` (26.11.2026) визначає **п'яту метрику** — час ітерації — і прямо фіксує: *«Замірів за цим протоколом ще немає — жодного числа тут не наведено»*. Протокол вимагає:

- медіану **і** p90, а не середнє (хвіст важливіший за типовий випадок);
- окремо теплий і холодний стан, N ≥ 20;
- фіксовану машину, toolchain, прапорці, governor;
- заборону порівнювати числа з інших репозиторіїв, машин або прапорців.

Той самий документ містить правило, яке прямо б'є по вихідному тексту: **не переводити зекономлені секунди в «роки життя»**, і цитувати вартість переривання лише зі статті (25:26 ± 54:48, Mark/Gonzalez/Harris, CHI 2005), а не з інтерв'ю.

Отже: теза «FPC швидший для ітерації» **не хибна — вона невиміряна**. У репозиторії, який щойно зафіксував, що міряти це ще не почали, подавати її як «стратегічну перевагу» означає зробити рівно те, проти чого написаний протокол.

**Що це означає практично**: перший крок — не суперечка про мови, а **замір**. Стенд для часу ітерації (FPC проти нативного backend на тому самому Canon) дає число, після якого рішення стає арифметикою, а не смаком.

## 6. Що мусило б статися, щоб ADR-004 змінився

ADR-004 не змінюється текстом. Він змінюється рішенням власника після трьох умов:

1. **Замір часу ітерації** за протоколом `chas-iteratsii.uk.md`, з медіаною, p90 і сирим виводом у `evidence/`. Без числа питання «швидше» не існує.
2. **Свідок, що Pascal-шар не краде семантичну владу**: той самий Canon, той самий `(canon-conforms?)`, доведений через FPC — тобто M0 із ADR `wsm-lazarus`, а не новий паскалівський Lisp.
3. **Явна ціна**: третя мова в production означає третій набір гейтів, третій компілятор у ланцюзі довіри і третю кваліфікацію для власника. ADR-004 свого часу виник саме тому, що «тимчасовий Rust» виріс у 9 crate-ів і дублікат evaluator-а. Це не гіпотеза — це вже сталося одного разу.

Доки цих трьох пунктів немає, теза лишається **пропозицією**, а не архітектурою.

## 7. Фальсифікаційні тести

| # | Тест | Що спростовує |
| :--- | :--- | :--- |
| T1 | Медіана часу ітерації FPC ≤ 2× медіани нативного backend на тому самому Canon | тезу «FPC дає стратегічну перевагу в ітерації» |
| T2 | FPC-свідок проходить `(canon-conforms?)` на pinned Canon без паскалівського дублювання семантики | тезу «FPC-шар може бути основою, а не свідком» |
| T3 | Pascal-шар додає ≤ N гейтів і ≤ M рядків до ланцюга довіри без нових обходів | тезу «третя мова не коштує нічого» |
| T4 | Для кожного підтвердженого проєкту (§1) за першоджерелом описати privilege boundary, syscall boundary, ізоляцію процесів/застосунків і модель доступу до ресурсів | тезу «FPC-ОС — це вже вирішена задача»; тест не дозволяє узагальнювати модель одного unikernel на всі Pascal-системи |

T4 — це перевірка меж довіри, а не наперед заданий висновок. Сучасний TORO unikernel запускає застосунок на тому самому privilege level і замінює syscall звичайними викликами функцій; окремий ToroOS має одне CPU-ядро, а SMP/networking у його README залишені як work in progress. Ultibo — bare-metal середовище, яке надає системні послуги прикладній програмі, але не позиціонує себе як general-purpose OS. FPOS прямо попереджає про частини реалізації, непридатні для використання. FP-RTOS не можна використовувати в цьому аргументі до перевірки першоджерела. Ці приклади демонструють придатність FPC для окремих системних моделей, але не доводять готовність до повноцінної загальної ОС.
